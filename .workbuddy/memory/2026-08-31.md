## 后台键鼠失效修复（改 SendInput 方案）
- 问题：鼠标/键盘后台操作没生效。
- 根因（两个）：
  1. **坐标 bug**：`background_click` 把屏幕坐标直接当客户区坐标编码 lParam，点击整体偏移「边框+标题栏」。
  2. **PostMessage 对现代应用无效**：Windows 11 记事本是 UWP，没有标准 Edit 子窗口，PostMessage 投递的 WM_KEYDOWN/WM_CHAR 根本触发不了输入。之前冒烟测试只断言「发送成功」没验证「实际生效」，误判了。
- 修复：
  - `win_actors.py` `background_click`：x/y 语义改为**屏幕坐标**（None=当前鼠标位置），内部 ScreenToClient 转客户区坐标；点击前加 WM_MOUSEMOVE。`background_press`：lParam 加扫描码（MapVirtualKeyW）+ KEYUP 释放标志（很多程序检查扫描码，置 0 会被忽略）。
  - 新增 `activate_window(hwnd)`（AttachThreadInput 绑定线程 + SetForegroundWindow + SetFocus，绕过「后台进程不得抢前台」限制）和 `restore_foreground()`。
  - `tasks.py` `run_click_step`/`run_press_step` 后台分支改为：**循环前 activate_window 一次 → 循环内 input_actors(pynput/SendInput) 发送 → finally restore_foreground**。这样对 Chrome/UWP/经典 Win32 都生效（SendInput 是系统级注入）。
  - `flow_dialog.py` 后台 tooltip 更新：说明会短暂把目标窗口带到前台（结束后还原）。
- 关键认知：**PostMessage 是「真后台不抢焦点」但只对经典 Win32 有效；SendInput+激活是「伪后台短暂抢焦点」但对现代应用生效**。纯 DirectInput 游戏两者都基本无解（需驱动级）。
- 验证：UWP 记事本（PostMessage 无效）用新方案成功输入 abc；run_press_step/run_click_step 后台端到端（输入 5 次 x + 点击固定坐标）通过；21 测试全通过。

## 打包版支持 OCR：PaddleOCR → RapidOCR 改造（含打包失败修复）
- 需求：用户要打包版带 OCR，但 PaddleOCR（paddlepaddle+torch+模型）打进 onefile 会 1GB+、构建时间翻几倍。选定方案：**改用 RapidOCR（rapidocr_onnxruntime）**——onnxruntime CPU 推理跑同一个 PP-OCRv4 模型，精度一致，依赖只有 onnxruntime(~43MB)+模型(~15MB)。
- 环境坑（pip 在 Windows 沙箱里卸载/覆盖会 safe-delete 失败）：装 rapidocr 时 pip 把 numpy 升到 2.5.2、opencv 升到 4.10，还误删了 six/requests_file/typing_extensions 的模块文件（只剩 dist-info）→ 修复：`pip install <pkg> --no-deps --ignore-installed`（只新增文件不触发卸载）；目录删不掉用 **rename 改名绕过**（numpy → numpy.old-2.5.2，再装 1.26.4，最后 rm 掉 .old）。
- **打包失败根因链（三个依次排查）**：
  1. numpy 2.5.2 用 PEP 695 TypeAlias 语法（`type NDArray[ScalarT]=...`），Nuitka 2.7.11 `assert not node.type_params` 崩溃 → **降回 numpy 1.26.4**（回到已验证组合，opencv 4.10 兼容 numpy 1.26）。
  2. onnxruntime/__init__.py 在 cpuinfo+py3nvml 存在时 `from .transformers.machine_info import get_device_info`（→tensorflow→keras），Nuitka 递归分析 keras 卡死/FATAL → **`--include-module=onnxruntime` + `--include-package=onnxruntime.capi`（不整包分析）+ `--nofollow-import-to=onnxruntime.transformers,torch,tensorflow,keras,cpuinfo,py3nvml`**。
  3. 手动 `--include-data-files` 指定 onnxruntime.dll 与 Nuitka dll-files 插件自动检测的 DLL **冲突**（FATAL: conflicts with dll）→ **删掉手动 DLL 参数，交给 Nuitka 自动处理**（会打印 "Found 2 files DLLs from onnxruntime installation"）。
- build.py 改动：`_ocr_include_args()` 从「排除 paddleocr/torch」改为「包含 rapidocr_onnxruntime + onnxruntime 核心 + 模型数据文件」；`_rapidocr_data_args()` 带 3 个 .onnx + config.yaml；`_onnxruntime_dll_args()` 返回空（注释说明交给 Nuitka）；REQUIRED_MODULES 加 rapidocr_onnxruntime/onnxruntime。
- ocr.py：is_available/_get_ocr/recognize/_extract_texts 换 RapidOCR（`[[box, text, score],...]` 格式），去掉 torch/oneDNN hack；lang 参数保留但默认中英混合模型不区分。
- 结果：**打包成功，产物 100.7MB**（原 80.6MB 只涨 20MB，远非 1GB），首次带 OCR 构建 15 分钟；exe 启动正常；onefile 解压目录确证含 onnxruntime.dll/pyd + 3 个 .onnx 模型 + config.yaml；177 测试全通过。
- 经验：**Nuitka 打包 onnxruntime 类大包用「include-module 精确入口 + nofollow 重型子包」，不要整包 include-package**；**Nuitka 自动检测第三方 DLL，别手动 include-data-files 同一文件**。
- 遗留：ocr.py 文件头带 UTF-8 BOM（原有），Python 能正常 import（utf-8-sig 解码），不影响运行。
